## 1. 사용 순서

1. **`upstream/frontend-design-SKILL.md` 를 먼저 끝까지 읽고 그대로 따른다.** 미학 판단의 정본은 원본이다. 이 문서는 원본을 대신하지 않는다.
2. 아래 §2~§8의 더존 보강을 함께 적용한다.
3. 산출물이 원피스·PPTX로 이어지면 §7의 전용 스킬·표준을 추가로 따른다.

**우선순위** — 서로 부딪히면 위가 이긴다.

| 순위 | 근거 | 예 |
|---|---|---|
| 1 | 매체의 하드 제약 | 원피스: 흰 바탕·인라인 스타일·외부 서체 금지 / PPTX: 좌표·서체 임베드 |
| 2 | 사용자 지시·브리프 | 「파란 계열로」, 「이 양식대로」 |
| 3 | 브랜드·사내 양식(§2) | EQT 발표 템플릿, 공식 보고 양식 |
| 4 | 원본(`upstream/`) | 주제 기반 설계, 피할 기본값, 절제, 품질 하한 |
| 5 | 이 문서의 더존 보강(§3~§8) | 한국어 타이포, 인쇄, 표기 |

매체 제약은 지키지 않으면 문서가 깨지므로 지시로도 바꾸지 않는다. 지시가 제약과 부딪히면 그 사실을 사용자에게 알린다. 원본도 「브리프가 정한 방향은 항상 이긴다」고 한다. 2~3은 원본의 그 원칙을 더존 환경에 적용한 것이다.

## 3. 주제에서 출발하기 — 더존 산출물의 소재

원본은 「주제·업계·소재·고유 어휘에서 방향을 끌어내라」고 한다. 더존 산출물에서 그 소재가 되는 것들이다. 매번 같은 소재로 수렴하지 않도록, 브리프의 실제 내용에서 하나를 골라 설계안에 이유를 적는다.

- **업무 소재**: 결재선과 결재 도장, 문서함·서류철, 법무의 사건 기록·기일표, CRM의 영업 단계·파이프라인, 일정의 달력 격자, 회계 원장·전표
- **제품 소재**: Amaranth 10 화면의 실제 구성(GNB·LNB·목록·상세), 실제 데이터의 모양(건수·상태값·코드)
- **독자**: 경영진(결론과 판단 근거), PM·기획(범위·일정·결정 사항), 개발자(구조·수치·재현 방법), 고객사(대외 어휘·브랜드)

주제가 불분명하면 원본대로 주제·독자·주된 용도를 제안하고 사용자에게 확인한다.

## 4. 더존 산출물에서 자주 나온 기본값 — 피할 것

원본의 「AI 기본값」 목록이 더존 산출물에서 실제로 나타난 모습이다. **§2의 브랜드·양식이 정한 경우가 아니면 쓰지 않는다.**

| # | 나타난 모습 | 원본의 어느 기본값에 해당하나 (①~⑤ = 동봉 원문 「For calibration」 목록 번호, 그 밖은 원문의 해당 대목) | 실제 예 |
|---|---|---|---|
| 1 | 따뜻한 종이색 바탕 + 세리프 제목 + 테라코타·적갈색 강조 | ① 크림 바탕 + 세리프 + 테라코타 | 이 스킬 0.1.0판이 권장한 `#f4ecdc` + `#b54822` 「Editorial Gravity」 |
| 2 | 신문식 헤어라인 구분선 + 각진 모서리 + 빽빽한 단 | ③ 신문식 레이아웃 | 0.1.0판의 「헤어라인으로 정보 구분」 권장 |

| 5 | 제목 속 한 단어만 다른 색·기울임 | 타이포그래피 함정 | 제목 강조어만 와인색 |

한국어에서 주의할 점이 세 가지 있다. 한글에는 대문자가 없어서 원본의 「대문자 라벨」 함정은 **넓은 자간의 작은 색 라벨이 모든 제목 위에 반복되는 모습**으로 나타난다. 그리고 한국어 문장 속 나열에 쓰는 가운뎃점은 함정이 아니다. 함정은 **메타 정보를 장식처럼 이어 붙인 줄**이다(원문은 'A · B · C' 꼴만 들고 위치·항목은 정하지 않는다 — 문서·구획 머리의 날짜·분류·작성자 줄이 흔한 예이고, 카드·목록에 붙는 메타 줄도 같다). 한 항목의 데이터 값(이름·회사·부서)을 가운뎃점으로 이은 줄은 원문이 따로 다루지 않는다. 원문의 기준은 주제와 상관없이 붙는 장식 줄인지이므로, 카드·목록 항목마다 같은 꼴로 붙는 요약 줄이면 함정 쪽으로 보고 표의 열이나 짧은 라벨로 나눌 수 있는지 먼저 본다. 문장 속 나열과 표 칸 안의 값은 함정이 아니다. 줄표도 같다 — 문장 안에서 앞말을 풀어 주는 줄표는 문장 부호라 함정이 아니고(EQT 원본 10쪽 부제처럼), 짧은 라벨과 조각을 줄표로 이어 붙인 꼴(12행)이 함정이다. 브리프 문구에 줄표가 있으면 그것이 표기를 정한 것인지 주제를 설명한 것인지 가린다. 사용자가 정해 준 제목이면 바꾸기 전에 확인을 받고(§1 2순위), 주제 설명이면 12행대로 고친다.

## 5. 한국어 타이포그래피

- **서체는 후보에서 고르고 이유를 적는다.** 어떤 산출물에나 쓰는 기본 서체는 두지 않는다. 산세리프 후보는 Pretendard, Noto Sans KR, IBM Plex Sans KR, 나눔스퀘어 네오이고, 명조 후보는 Noto Serif KR, 마루부리다. 사내 서체는 DOUZONE Title·Text(§2)다. 원본대로 한두 가족이면 충분하고, 둘이면 확실히 다르게 쓴다.
- **줄높이**: 한국어 본문은 1.6~1.7로 둔다. 라틴 문자 본문보다 조금 높게 잡는다. 명조 본문은 원본대로 고딕보다 조금 더 높인다.
- **행 길이**: 원본은 행 길이를 기본 80자 미만으로 두고, 세리프 서체는 조금 더 길어도 된다고 한다(영문 글자 수로 읽는다 — 원문은 문자 종류를 따로 적지 않는다). 한글은 글자 폭이 라틴 소문자(약 0.5em)보다 훨씬 넓어 **공백 제외 40자 안팎을 기본 상한**으로 보고, 명조 본문은 원본대로 조금 더 길어도 된다. CSS로는 본문 단에 `max-width: 40em` 을 준다. 한글 한 글자 폭은 Apple SD Gothic Neo 0.865em·Pretendard 0.864em·DOUZONE Text 0.900em·Noto Sans KR 0.920em이다(뒤 셋은 `규칙/폰트` 파일). 2026-10-03 실측(Chrome, 16px, `word-break: keep-all`, 워크스페이스·플러그인 문서에서 뽑은 문단, 마지막 줄을 뺀 줄 평균)으로 40em 한 줄에는 한글만 있는 글이 공백 포함 약 50~56자·공백 제외 약 37~41자, 문장 부호가 섞인 글(부호 4~12%)이 약 51~57자·39~45자 들어간다. 공백 제외로 세면 Apple SD Gothic Neo·Pretendard 보다 Noto Sans KR 은 2~3자, DOUZONE Text 는 1~2자 적다. 영문·숫자가 많은 글(31~57%)은 표본에 따라 한 줄 공백 제외 17~80자, 문단 평균 44~63자까지 흩어지므로(끊기지 않는 긴 식별자가 있으면 줄이 더 짧아진다) 범위를 정해 두지 않고 실제 렌더로 본다. 0.2.3 을 처음 쓸 때 적은 글 종류별 값은 문장 하나의 첫 줄 용량을 잰 것이라 버렸다. 「몇 자」는 공백을 빼고 센다.
- **줄바꿈**: 한국어 본문에는 `word-break: keep-all` 을 써서 단어 중간에서 끊기지 않게 한다.
- **숫자**: 표·수치는 `font-variant-numeric: tabular-nums` 로 자릿수를 맞춘다.
- **영문 장식 라벨 금지**: 한국어 문서에 장식용 영문 라벨을 넣지 않는다. 라벨이 필요하면 의미 있는 한국어로 쓴다. 예외는 §2 표의 사내 기준이 정한 이름뿐이다(예: Market Brief 양식 이름, EQT 표지 브랜드 슬로건 「Authentic innovation, / AX and More」, EQT 카드 안 영문 대문자 소제목).
- **서체 불러오기**: 외부 CDN 서체는 열람 환경에 따라 불러오지 못할 수 있다. 시스템 서체 대체를 함께 지정하고, 원피스로 옮길 문서는 원피스 표준의 시스템 서체를 쓴다.

**인쇄 친화 (자체 완결 HTML)**: 더존 보고서는 PDF 변환·인쇄가 따라오는 경우가 많다. `@media print` 에서 장식 배경을 빼고, `page-break-inside: avoid` 로 섹션·표가 쪽 사이에서 잘리지 않게 한다. 원피스 문서는 `@media` 를 쓸 수 없으므로 원피스 표준을 따른다.

**쪽수 제약이 있을 때** (예: 「1쪽 요약」): 문서에 `@page { size: A4; margin: … }` 를 꼭 적는다 — 없으면 headless Chrome 이 Letter(612×792pt)로 출력해 다른 용지로 판정하게 된다. PDF로 출력해 쪽수를 직접 센다 — Chrome `--headless=new --print-to-pdf=out.pdf file://…` 로 뽑고 `python3 -c "import re,sys;print(len(re.findall(rb'/Type\s*/Page[^s]',open(sys.argv[1],'rb').read())))" out.pdf` 로 센다. 자주 걸리는 함정 셋: ① 화면용으로 px로 고정한 글자 크기가 인쇄에서도 그대로라 본문과 보조 글자의 크기 위계가 뒤집힐 수 있다(2026-10-02 검증 샘플에서 보조 글자가 본문보다 커졌다). ② 화면용 좁은 화면 규칙(`@media (max-width: 760px)` 등)이 인쇄에도 걸린다 — headless Chrome `--print-to-pdf` 에서 미디어 쿼리가 보는 폭은 약 741.3px였다(기본 Letter 816px 에서 기본 여백 약 1cm 씩 뺀 값). CSS `@page` 로 용지·여백을 바꿔도 같았다(2026-10-02·10-03 실측: A4 13mm·A3 여백 0·지정 없음·A5 30mm·Letter 여백 0·A4 가로. 본문 배치 폭은 `@page` 를 따라 A4 13mm 에서 약 696px). 그래서 기준이 742px 이상인 `max-width` 규칙은 인쇄에 걸리고, 741px 이하 규칙은 걸리지 않는다. 인쇄 요청 자체에 용지·여백을 주면(CDP `Page.printToPDF`·Puppeteer `page.pdf`) 폭이 바뀐다 — A4 여백 0 은 약 794.7px, Letter 여백 0 은 816px, A3 여백 0 은 약 1122.7px 이다(그래서 `max-width: 794px` 규칙은 A4 여백 0 인쇄에 걸리지 않는다). 좁은 화면 규칙은 `@media screen and (…)` 로 한정한다. ③ `page-break-inside: avoid` 를 큰 구획에 걸면, 남은 자리에 들어가지 않는 구획이 다음 쪽 첫머리로 밀리고 앞 쪽에 빈자리가 남는다. 그런 구획이 여럿이면 쪽수가 는다(실측: 0.55쪽 구획 3개에서 2쪽이 3쪽으로). 한 쪽보다 큰 구획은 다음 쪽에서 시작한 뒤에도 결국 잘린다 — 쪽수 제약이 있으면 표·그림처럼 작은 단위에만 건다. 덧붙여 headless `--print-to-pdf` 는 배경을 그대로 찍지만, 사람이 Chrome 인쇄 대화상자로 뽑으면 「배경 그래픽」이 기본으로 꺼져 있어(켜 두면 그 선택이 유지된다) 배경으로 그린 칠·그림이 빠지고 밝은 글자는 어둡게 바뀌어 찍힌다(Chromium 인쇄 미리보기 기본값과 같은 설정의 출력으로 확인 — 대화상자를 직접 조작하지는 않았고, Safari·Firefox 는 확인 못 함). 배경으로 정보를 그렸다면 그 요소에 `print-color-adjust: exact` 를 준다. 페이지 전체 바탕이면 `html`(`:root`)에 준다 — `body` 에만 주면 바탕은 빠지고 자식 요소에만 적용된다. 접두사 없는 표기는 Chrome 136·Safari 15.4·Firefox 97 부터 지원한다. 그보다 오래된 Chrome·Safari 까지 맞출 때만 `-webkit-print-color-adjust: exact` 를 함께 적는다(Firefox 48~96 은 `color-adjust: exact` — Firefox 는 `-webkit-` 표기를 지원하지 않는다).

## 8. 마무리 점검

원본의 품질 하한(모바일 반응형 · 키보드 포커스 · 모션 줄이기 존중 · 시각 접근성 · 조화로운 색)에 더해 아래를 확인한다.

- [ ] 설계안에 근거(§2 또는 §3)와 제약 칸이 있는가
- [ ] §4 표의 기본값이 브랜드·양식 근거 없이 들어가 있지 않은가 — §4 표에 없는 것도 동봉 원문의 「For calibration」 목록(①~⑤), 타이포그래피 함정 3종, 히어로 기본 처리(17행)로 한 번 더 대조한다
- [ ] 글자와 바탕의 대비가 4.5 이상인가 — 큰 글자(굵게 18.7px(14pt) 이상, 보통 굵기 24px(18pt) 이상)는 WCAG 1.4.3(AA) 대로 3 이상이면 된다(AAA 1.4.6 은 큰 글자도 4.5). 「굵게」는 font-weight 700 이상으로 본다 — WCAG 는 굵기 값을 정하지 않으므로 CSS `bold`(700)와 axe-core 의 기준(700)을 따른 것이다. WCAG 정의에는 한중일 서체는 「같은 크기에 해당하는 값」이라는 단서가 있는데, 이 문서는 라틴 기준 px를 그대로 쓴다. 흐린 보조 글자까지 각자 얹히는 면 기준으로 잰다. 막대·선·아이콘 같은 그림은 내용을 이해하는 데 필요한 것만 3 이상(WCAG 1.4.11 — 장식용 구분선은 대상이 아니다). 입력란 테두리(그 칸이 입력란임을 알리는 표시일 때), 포커스 표시, 선택·체크 상태 표시도 인접한 색과 3 이상이다(WCAG 1.4.11 UI 구성 요소 — 비활성 요소와 브라우저 기본 모양은 제외). 버튼은 글자·아이콘으로 알아볼 수 있으면 테두리 대비를 요구하지 않고, 테두리가 버튼을 알아보는 유일한 표시일 때만 3 이상이어야 한다. 글자·숫자로 된 아이콘(숫자 배지·단계 번호·닫기 X 등)은 글자 기준으로, ✓·● 같은 기호는 그림 기준으로 잰다. WCAG 는 모양으로만 쓰인 글자(닫기 X·> 화살표·ⓘ)를 그림(1.4.11)으로 보므로, 글자 모양 아이콘을 4.5 로 재는 것은 WCAG 보다 엄격한 이 문서의 선택이다. 눈으로 판정하지 않고 계산한다(WCAG 상대 휘도 식 — 계산 스크립트는 `dz-progress-dashboard` §9.2). 페이지에 쓰인 색 쌍을 빠짐없이 모으려면 글자 노드와 `::before`·`::after` 글자를 함께 훑는다. `content: ""` 로 테두리·배경만 그리는 의사 요소는 그림으로 보고 그 테두리·배경색을 잰다
- [ ] 모바일 폭(390px)에서 가로 넘침이 없는가 — `document.documentElement.scrollWidth <= innerWidth` 로 판정한다. 헤드리스 Chrome 의 `--window-size=390,…` 은 실제 폭이 500px로 잡혀 오판한다(2026-10-02 실측). 390px 폭 iframe 에 넣거나 브라우저 창 크기를 줄여 잰다. `file://` 페이지를 iframe 으로 재려면 Chrome 에 `--allow-file-access-from-files` 를 줘야 iframe 안 문서를 읽을 수 있다. headless 에서 결과를 꺼내려면 측정 스크립트를 넣은 부모 페이지를 `--dump-dom --virtual-time-budget=5000` 으로 열고, iframe 안 글꼴이 다 불러와질 때까지(`document.fonts.ready`) 기다린 뒤 결과를 DOM 에 적는다
