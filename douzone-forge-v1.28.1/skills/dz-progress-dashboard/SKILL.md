# 범용 진행 대시보드 (dz-progress-dashboard)

> **의존 SSoT**: `참고자료/리포트/2026-06-01-dz-progress-dashboard-스킬설계안.md` §11 범용 재정의(설계 근거) · `규칙/프로세스/HTML-원피스-작성-표준.md` D-02(미학 — frontend-design 1차 인용) · `CLAUDE.md` 「범용 진행 대시보드 운영」 절(발동 지침)

> **용어 풀이**: 대시보드(진행을 한 화면에 그려 보여주는 현황판) · 마커(HTML에 심어두는 `<!-- 표식 -->`, 갱신 위치를 가리킴) · 부분 치환(전체를 다시 만들지 않고 표시 부분만 바꿈) · 멱등(같은 입력이면 여러 번 돌려도 결과 같음) · TaskList(이 세션의 할 일 목록 도구) · 순수 칸 비율(완료 칸 ÷ 전체 칸) · 표시본(브라우저가 읽는 사본)

## 0. 한 줄 정의

복잡하거나 단계가 많은 작업을 **시작할 때 대시보드를 만들어 보여주고, 단계가 바뀔 때마다 자동으로 갱신해 다시 보여준다.** 특정 프로젝트 전용이 아니라 **모든 다단계 작업에 쓰는 범용 도구**다.

## 1. 트리거 / 발동

**사용자 호출** (한글 키워드):
- "대시보드 만들어줘" · "진행 대시보드" · "대시보드 갱신·반영" · "진행 가시화" · "대시보드 보여줘"

**자동 발동** (자비스 판단 — §6 신호 3개 이상):
- 다단계·다영역 작업을 감지하면 자비스가 먼저 **"대시보드로 추적하겠습니다" 1줄 고지** 후 생성

**상위 대시보드 우선** (생성 전 필수 점검 — 2026-06-02):
- 이미 상위(프로젝트·사이클) 대시보드가 있으면 **하위 작업 대시보드를 새로 만들지 않는다.** 상위 대시보드의 해당 항목 상태만 변경해 일관을 유지한다 (예: 기획·설계 표준화 #3 ⓒ출력 = 상위 매트릭스 #3 행만 ●로 갱신).
- 발동 판단 전 상위 대시보드 존재 여부를 먼저 확인한다. 하위 생성은 상위가 없을 때만.

## 2. 영역 분리 (기존 현황 스킬과 — 중복 회피)

| 스킬 | 영역 | 단위 |
|---|---|---|
| `dz-status-reporter` | 종합·인벤토리 (텍스트 보고) | 전사 |
| `dz-status-show` | 4 축 현황 시각화 (스냅샷) | 전사·세션 |
| **`dz-progress-dashboard`** (본 스킬) | **단계 진행 HTML 대시보드 (자동 생성·갱신)** | **개별 작업** |

→ status 계열 = "지금 전체 어디"(스냅샷). 본 스킬 = "이 작업이 어디까지"(작업 1건의 단계 흐름·자동 갱신).

## 3. 동작 흐름 (5 단계)

```
작업 시작
 → ① 복잡도 판단 (§6 신호 3개 이상)
 → ② 복잡하면 작업 유형 선택 (§4 카탈로그) + "대시보드로 추적합니다" 고지
 → ③ 공통 코어(§5) + 유형 변주로 대시보드 생성 → 표시
 → ④ 단계 전환마다 자동 갱신 + 표시 (완전 자동)
 → ⑤ 작업 종료 시 개인 세션에 보관 (§11)
```

## 4. 작업 유형 카탈로그 (6 종 — 자비스가 고름, 무한 변형 아님)

| 유형 | 예시 | 유형 특화 영역 (공통 코어에 더함) |
|---|---|---|
| 분석형 | 시장조사·벤치마킹 | 조사 단계 + 출처 격자 + 검증 상태 |
| 산출물 파이프라인형 | md→html→원피스→pptx | 단계 흐름 띠 + 산출물별 완료 체크 |
| 설계형 | 요구사항→IA→화면설계 | 산출물 단계 + 검토 게이트(G-입력·G-출력) |
| 개발형 | TDD 구현 | RED→GREEN→REFACTOR + 빌드·테스트 상태 |
| 표준화·다영역형 | 다영역 표준화 | 영역 분할 진행바 + 산출물 매트릭스 |
| 일괄·마이그레이션형 | 다수 파일 일괄 변환 | 대상 목록 + 진행률 + 완료/실패 카운트 |

> 애매하면 사용자에게 한 번 확인. 카탈로그에 없는 작업은 가장 가까운 유형 + 공통 코어만으로. 카탈로그 확장은 별도 결정.

## 5. 공통 코어 (어떤 유형이든 같은 5 요소)

작업 목록(TaskList)에서 바로 도출:
1. **진행바** — 전체 진척 % (§7)
2. **단계 목록** — 할 일별 상태 (완료·진행·대기)
3. **현재 위치** — 지금 어느 단계
4. **다음 단계** — 바로 다음 + 선택지
5. **갱신 시점·주체**

> ⛔ **완료를 두 가지로 표시하지 않는다** — 체크박스 하나로 통일하고 배지는 우선순위 전용이다(§7.1). 한 행에 체크박스와 「✅ 완료」 배지를 함께 두면 **둘이 어긋나 진행률이 거짓말을 한다**(2026-08-14 실사고).

## 6. 판단 가이드 (언제 켜나 — 신호 3개 이상)

- 단계(할 일) **3개 이상**
- 여러 **영역·파일**에 걸침
- **장시간·여러 세션** 예상
- **산출물 다수**(보고서·발표자료 등)
- 사용자가 "복잡하다" 언급

→ 3개 이상이면 **"대시보드로 추적하겠습니다" 1줄 고지** 후 생성 (자율이되 투명 — 원치 않으면 끔).

## 7. 진행률 산정 (순수 칸 비율 — 확정)

**완료 칸 ÷ 전체 칸**. 손어림·가중 없음.
- 단순 작업: 완료 task ÷ 전체 task
- 단계 매트릭스형: 완료 셀 ÷ 전체 셀 (예: 6/21 = 29%)

> 진행률 밖 성과(인프라·표준 신설 등)는 진행바에 섞지 않고 **별도 성과 배지**로 표기 — 진행바는 정직한 칸 비율만.

### 7.1 ⛔ 완료 표시는 **체크박스 하나로 통일** (2026-08-14 확정 — 차민수 지시)

> 신설 계기: 한 행에 **체크박스와 「✅ 완료」 배지가 둘 다** 있었고, **서로 다른 값을 세고 있었다.** 실측 — 배지(파일 기록 `lv="grn"`) 5건인데 체크박스는 0건이라 **진행률이 「0 / 15 (0%)」로 거짓말**을 했다. 원인은 「체크는 사용자가 하는 것」이라며 초기 씨딩(`PRESET`)을 없애면서 **진행률 기준을 함께 바꾸지 않은 것**이다.

**규칙 넷.**

1. **완료 표시는 체크박스 하나.** 「✅ 완료」 배지를 따로 두지 않는다. 완료는 **체크 + 취소선**으로만 나타낸다.
2. **배지는 우선순위 전용.** `🔴 오늘 · 🟠 지남 · 🟡 이번주 · 🟢 여유` 만 쓴다. 완료돼도 **원래 우선순위를 유지**한다 — 「오늘 마감이었던 것을 끝냈다」와 「여유 건을 끝냈다」는 다른 정보다.
3. **진행률은 체크 수 ÷ 전체.** 체크하면 즉시 오르는 것이 가장 직관적이다(수석 판단). 진행바·카운터·KPI 세 곳이 **같은 값**을 써야 한다.
4. **파일에 기록된 완료는 `PRESET` 로 씨딩한다.** 체크는 `localStorage` 에만 남아 공유되지 않으므로(§9 참조), 원천(그날 md ① 상태·미리알림)에서 완료된 건을 배열로 넣어 **첫 로드에 체크된 상태로 그린다.** 이후 사용자가 해제하면 그 뜻을 따른다.
   ```js
   const KEY="dw-{날짜}-v2";          // ★ 씨딩을 갱신할 때는 판번호를 올린다
   const PRESET=["A92255C6","28E64770"];   // 파일 기록 완료분
   let done;
   try{ var raw=lsGet(KEY); done = raw===null ? PRESET.slice() : JSON.parse(raw); }
   catch(e){ done=PRESET.slice(); }
   ```
   ⛔ **키 판번호를 올리지 않으면 씨딩이 무력하다** — 브라우저에 이미 저장된 옛 배열(예 `[]`)이 이겨서 아무것도 체크되지 않는다.

**예외 — 체크박스가 「완료」가 아닌 자리.** 「마감 지남 전건」처럼 **훑으며 후보를 고르는** 목록은 체크의 뜻이 다르므로 그대로 둔다. 대신 그 자리에는 **무엇을 위한 체크인지 한 줄로 적는다**(예 「끝난 것을 표시하면 그 목록으로 미리알림을 완료 처리합니다」).

## 8. 마커 기반 부분 치환 (구현 핵심 — 전체 재생성 ✗)

미학·정적 영역을 보존하려면 **동적 영역만** 마커 사이를 교체한다:
1. 동적 영역에 앵커 마커 1회: `<!-- DZ:키 -->값<!-- /DZ:키 -->`
2. 갱신 = 마커 사이만 데이터로 교체 (정적·CSS·여백 불변)
3. **멱등** — 같은 데이터면 결과 동일(diff 없음)

동적 영역 예(표준화·다영역형 1호 기준): 판본·날짜·진행률(바+%)·상세·매트릭스 셀·작업추적·카운트·현재위치·다음단계·footer.
정적(불가침): 의제·골격·`<style>`·범례.

**마커 한계 + 1호 적용 방식** (2026-06-01 실측): `<title>` 안·inline `style`(진행바 width)·class 속성엔 HTML 주석을 넣을 수 없다. 그래서 12곳에 마커를 일일이 넣는 대신, **대시보드 상단에 「DZ:DASHBOARD 갱신 맵」 주석 1개**로 동적/정적 영역 셀렉터(요소 주소)를 명시하고, 자비스가 그 맵을 보고 **셀렉터로 정밀 치환**한다. 텍스트·블록은 직접 치환, inline style·`<title>`은 셀렉터 기반. 마커(`<!-- DZ:키 -->`)는 텍스트 노드·블록에 선택 적용.

### 8.1 ⛔ 갱신 맵 주석 작성 규칙 (2026-07-27 실측 사고 — 반드시 지킬 것)

**HTML 주석은 중첩되지 않는다.** 갱신 맵 주석 안에 마커 예시를 문법 그대로 적으면 **그 예시의 주석 종료 기호에서 갱신 맵 주석이 조기 종료**되고, 남은 설명문이 본문 텍스트로 파싱되며(이 시점에 `<head>`가 닫힌다), 설명문 속 꺾쇠 태그명이 **실제 태그로 살아나 진짜 스타일 블록의 `:root` 변수 정의를 통째로 삼킨다.** 증상은 "색이 안 먹는 화면"이라 **테마 문제로 오진**하기 쉽다(실사고 — 테마를 바꿔도 동일 재현).

1. **주석 안에 주석 종료 기호를 쓰지 않는다** — 마커를 설명할 때는 꺾쇠·기호 없이 **이름만** 적는다. 예: `마커쌍 DZ:NOW : 현재 위치`
2. **주석 안에 꺾쇠 태그명을 쓰지 않는다** — 「스타일 블록」·「문서 제목 태그」처럼 **한글로** 적는다. 셀렉터(`#bar-fill`·`.step[data-step="N"]`)는 꺾쇠가 없으므로 그대로 써도 된다
3. **본문에 실제로 심는 마커쌍은 각각 독립된 주석이라 무해하다** — 금지 대상은 **"주석 안에서 주석을 인용하는 것"** 하나뿐이다

**안전한 갱신 맵 서식** (교정 정본 = `_개인/sessions/WEHAGOQ-발표문서v17-자산화/dashboard.html` 상단):

```
DZ:DASHBOARD 갱신 맵 - 자비스가 단계 전환 시 아래 위치만 정밀 치환한다.
  동적(치환 대상):
    - 문서 제목 태그                      : 진행률 % 반영
    - #hdr-updated                       : 갱신 시각
    - #bar-fill 의 인라인 width           : 진행률 %
    - #bar-pct / #cnt-done / #cnt-total  : 진행률 % · 완료 · 전체 칸수
    - .step[data-step="N"] 의 class 와 .step-state 텍스트
    - 마커쌍 DZ:NOW                       : 현재 위치
    - 마커쌍 DZ:NEXT                      : 다음 단계
  정적(불가침): 스타일 블록 전체 · 골격 · footer 고지문
  진행률 = 완료 단계 ÷ 전체 단계 (순수 칸 비율, 가중 없음)
```

위 내용을 문서 상단에서 **주석 하나로 감싼다** — 여는 기호·닫는 기호가 각각 1회씩만 나오면 된다.

> 위 §8 본문·§5의 마커 표기(`<!-- DZ:키 -->`)는 **마크다운 문서라 안전**하다. 대시보드 HTML의 **주석 안**에 옮겨 적는 순간 사고가 된다.

## 9. 표시 — 로컬 파일 직접(`open`) + 자동 갱신 (2026-06-20 보강) · 표시 직후 자가 검증 (2026-07-27 신설)

**원본 HTML을 `open` 으로 기본 브라우저에 직접 띄우되 — 최초 1회만.** 이후 단계 갱신은 **파일만 수정**하고 `open` 을 다시 부르지 않는다 (다시 부르면 같은 `file://` 가 새 탭으로 떠 탭이 누적된다 — 함정 ⑦).

```bash
open "원본경로/dashboard.html"   # macOS — 최초 표시 1회만. 이후는 파일만 갱신
```

**🔄 자동 새로고침 스크립트 (필수 — 모든 대시보드 HTML에 포함)**: 열려 있는 탭이 스스로 최신 파일을 다시 읽도록 `</body>` 직전에 아래를 넣는다. → 자비스는 **파일만 갱신**하고, 사용자가 그 탭으로 **돌아올 때** 자동 새로고침된다(재표시·새 탭 불필요).

⛔ **`file:` 에서는 `fetch` 로 「바뀌었는지」를 알아낼 수 없다** (2026-08-14 실측 확정 — §9.0 함정 ④).
Chrome 이 `file:` 스킴의 `fetch` 를 막아 `TypeError: Failed to fetch` 가 나고, `.catch(){}` 가 그것을 삼켜 **조용히 아무 일도 일어나지 않는다.** 그래서 **감지를 포기하고 「탭으로 돌아오면 무조건 다시 읽는다」** 로 간다.

⛔ **`location.reload()` 도 쓰지 않는다** — `file:` 에서 캐시를 타 무력하다(2026-08-11 실사고). 반드시 `location.replace(pathname + "?v=…")` 로 **새 URL 로 이동**한다.

```html
<head>
<!-- BUILD:20260811-160310 -->   <!-- 갱신마다 초 단위로 새로 찍는다 (사람이 판본을 읽는 용도) -->
```

```html
<script>
// 자동 새로고침 — file: 스킴 계약 (2026-08-14 교체)
// 감지(fetch)는 file: 에서 불가하므로, 탭 복귀 때마다 무조건 최신을 다시 읽는다.
(function(){
  var SK="dz-scroll", LK="dz-reload-ts", GUARD=4000;   // 키는 대시보드마다 날짜 등으로 구분
  try{                                                  // 재로드로 튄 스크롤 복원
    var y=sessionStorage.getItem(SK);
    if(y!==null){ sessionStorage.removeItem(SK); window.scrollTo(0, parseInt(y,10)||0); }
  }catch(e){}
  function tooSoon(){ try{ return Date.now()-(+sessionStorage.getItem(LK)||0) < GUARD; }catch(e){ return false; } }
  function refresh(){
    if(document.hidden || tooSoon()) return;            // ★ 되돌이표 차단
    try{
      sessionStorage.setItem(LK, String(Date.now()));
      sessionStorage.setItem(SK, String(window.scrollY||0));
    }catch(e){}
    location.replace(location.pathname + "?v=" + Date.now());
  }
  document.addEventListener("visibilitychange", function(){ if(!document.hidden) refresh(); });
  window.addEventListener("focus", refresh);
})();
</script>
```

**설계 지점 셋** — 하나라도 빠지면 못 쓴다.

| 지점 | 없으면 |
|---|---|
| **시각 도장 4초 가드**(`sessionStorage`) | 재로드 직후 `focus` 가 다시 발동해 **무한 재로드**가 된다. 페이지 안 변수로는 못 막는다 — 재로드로 초기화되므로 **재로드를 건너 살아남는 저장소**여야 한다 |
| **스크롤 복원** | 감지 없이 매번 재로드하므로 보던 위치가 매번 맨 위로 튄다 |
| **`?v=Date.now()`** | `file:` 캐시에 걸려 옛 내용이 그대로 나온다 |

**대가**: 탭에 돌아올 때마다 한 번 재로드한다(바뀐 게 없어도). 로컬 파일이라 비용은 무시할 수준이고, **「안 바뀌는 것」보다 낫다.**

ⓘ `http://` 로 띄우면 `fetch` 가 되므로 종전 「BUILD 비교」 방식도 쓸 수 있다. 다만 상시 서버가 필요해 **기본은 위 계약**으로 둔다.

- **갱신 후**: 파일만 Edit(+ `BUILD` 스탬프 2곳 갱신) → 사용자가 탭 복귀 시 자동 반영. **`open` 재호출 금지**(탭 누적 방지).
- ⚠️ 스크립트가 없거나 **옛 스크립트를 들고 있는 기존 탭은 스스로 못 고친다.** 그때는 새 탭을 만들지 말고 **AppleScript 로 그 탭을 찾아 URL 만 교체**한다.

```bash
osascript -e 'tell application "Google Chrome"
  repeat with w in windows
    repeat with t in tabs of w
      if URL of t contains "<파일명 일부>" then set URL of t to "<새 URL>?v=<BUILD>"
    end repeat
  end repeat
end tell'
```

### 9.0 ⛔ 자동 새로고침 함정 4건 — 이걸 모르면 갱신이 화면에 안 나온다 (2026-08-11 · ④ 2026-08-14)

파일을 갱신했는데 브라우저가 **옛 내용을 계속 보여준** 사고. 두 번 연속 재현됐고, 고치는 과정에서 세 번째 함정까지 나왔다. 종전 서술 「원본을 직접 보므로 항상 최신(캐시 우회 0단계)」는 **사실이 아니었다** — 이 문장이 사고의 뿌리였다.
**그리고 2026-08-14, ①~③을 다 지켰는데도 갱신이 안 되는 네 번째 함정이 나왔다 — 감지 단계 자체가 막혀 있었다.**

| # | 함정 | 관측 | 해법 |
|---|---|---|---|
| ④ | ⛔ **`file:` 에서 `fetch` 가 막혀 감지가 아예 안 된다** | 탭에 탐침을 심어 재보니 `FETCH_FAIL TypeError: Failed to fetch`. 화면은 로드 시점(12:49)에 **반나절 멈춘 채**였고, 그동안 파일은 세 번 갱신됐다. **스크립트는 정상 실행 중**이었다(목록 15·55행 렌더 확인) — 즉 스크립트 결함이 아니라 **감지 수단이 못 쓰는 것**이었고, `.catch(){}` 가 실패를 삼켜 **신호가 하나도 안 남았다** | **감지를 포기한다.** 「탭 복귀 시 무조건 `location.replace(pathname+"?v="+Date.now())`」 + **4초 시각 도장**(되돌이표 차단) + **스크롤 복원**(§9 계약) |
| ① | **`location.reload()` 가 캐시를 쓴다** | reload 후 화면은 옛 내용. `location.href = …?v=` 도 안 먹는 경우 있음 | **`location.replace(pathname + "?v=" + 새값)`** — 새 URL 로 이동 |
| ② | **마커를 「분 단위 시각」으로 쓰면 같은 분의 재갱신을 놓친다** | 표시 시각(`15:58`)을 비교값으로 쓰면 같은 분에 두 번 고친 두 번째가 감지 안 됨 | **초 단위 BUILD 스탬프** _(④ 이후로 BUILD 는 비교값이 아니라 **사람이 판본을 읽는 표시**로 남는다. 그래도 초 단위는 유지 — 같은 분의 두 갱신을 사람이 구분해야 하므로)_ |
| ③ | **HTML 스크립트를 문자열 치환으로 고치다 스크립트를 죽였다** | `h.index('}', h.index('.catch(()=>{});'))` 가 화살표 함수 안의 `}` 를 잡아 `});` 잔재 → 문법 오류 → **목록이 통째로 0행**(18행·44행 → 0) | 스크립트는 **함수 전문을 앵커로 통째 교체**. 부분 index 계산 금지 |

### 9.1 표시 직후 자가 검증 (3 항목 — 눈 대신 계산값으로, 2026-07-27 신설)

최초 표시 직후 **반드시** 아래 3가지를 확인한다. 눈으로만 보면 "색이 좀 이상하다"로 넘어가 **스타일이 아예 안 먹은 상태**(§8.1 사고)를 테마 문제로 오진한다.

| # | 확인 | 정상 | 이상이면 |
|---|---|---|---|
| ① | `document.head` 자식에 **문서 제목 태그·스타일 블록**이 들어 있는가 | `META…, TITLE, STYLE` | 주석 조기 종료 → §8.1 규칙으로 갱신 맵 주석 교정 |
| ② | **`:root` 변수가 값을 반환**하는가 | `--tx` → `#152232` 류 | **빈 문자열이면 스타일 블록 파손** (유령 태그가 삼킴) |
| ③ | 주요 요소 **대비비가 4.5 이상**인가 | 전 항목 ≥ 4.5 | §9.2 기준으로 보조 색 단계 조정 |

**브라우저 계산값 조회** (서버 폴백 또는 인앱 브라우저에서):

```js
[...document.head.children].map(e => e.tagName).join(',');            // ① TITLE·STYLE 포함해야 정상
getComputedStyle(document.documentElement).getPropertyValue('--tx');  // ② 빈 문자열이면 파손
document.styleSheets[0].cssRules[0].selectorText;                     // ② 보강 — ':root' 여야 정상
document.querySelector('style').parentElement.tagName;                // ① 보강 — 'HEAD' 여야 정상
```

**브라우저를 못 쓸 때 — 파일만으로 하는 사고 탐지** (2026-07-27 정상판·파괴판 양쪽으로 검증):

⚠️ ①②는 **파싱 결과**라 원본 글자만 봐서는 알 수 없다(파괴된 파일에도 제목·스타일 글자는 그대로 있다). 대신 **사고를 만든 원본 패턴 2가지**를 직접 잡는다 — 이 둘 중 하나라도 참이면 §8.1 사고다.

```bash
python3 - "경로/dashboard.html" <<'PY'
import re, sys
h = open(sys.argv[1], encoding='utf-8').read()
# ⓐ 주석 안에 주석 열기 기호가 또 있으면 이미 조기 종료가 일어난 것
nested = [m.group(1)[:40] for m in re.finditer(r'<!--(.*?)-->', h, re.S) if '<!--' in m.group(1)]
# ⓑ 브라우저와 같은 순서로 걷어낸 뒤 head 안에 맨텍스트가 남으면 주석 내용이 새어 나온 것
head = h[:h.find('</head>')] if '</head>' in h else h
t = re.sub(r'<!--.*?-->', '', head, flags=re.S)                     # 주석 (조기 종료 그대로 반영)
t = re.sub(r'<(style|script|title)\b.*?</\1>', '', t, flags=re.S)   # 스타일·스크립트·제목 블록 통째
t = re.sub(r'<[^>]*>', '', t)                                       # 남은 태그
leak = t.strip()
print('ⓐ 주석 안 주석 :', bool(nested), nested)
print('ⓑ head 맨텍스트:', bool(leak), repr(leak[:60]))
print('판정 :', '파손' if (nested or leak) else '정상')

```

> 브라우저를 쓸 수 있으면 위 3항목이 우선이다. **스타일 블록 내용 앞부분에 주석 설명문이 들어와 있으면** §8.1 사고가 확정 — 이 한 가지로 원인이 갈린다.

### 9.2 미학 기준 — 대비 4.5 하한 (물러난 톤 포함, 2026-07-27 신설)

미학 정본은 `규칙/프로세스/HTML-원피스-작성-표준.md` D-02(frontend-design 1차 인용)를 따르되, 대시보드는 **읽히는 것이 최우선**이므로 아래를 하한으로 둔다.

- **물러난 톤도 대비 4.5 이상.** 대기 상태 배지·하단 고지문·단계 설명처럼 **시각적으로 물러나야 하는 요소도 읽을 수는 있어야** 한다. "흐리게"가 "안 보이게"가 되면 안 된다.
- **위계는 유지하고 최저값만 끌어올린다** — 강조·보조·흐림의 3단 위계를 뭉개지 말고, 가장 흐린 단계가 4.5에 닿도록 두 단계를 함께 진하게 조정한다.
- **각 요소의 "제 배경"으로 잰다.** 페이지 배경이 아니라 그 요소가 실제로 얹히는 면(카드 흰색·배지 자체 배경)으로 계산해야 한다. 같은 색도 배경이 바뀌면 통과·미달이 갈린다 — 아래 `--tx3` 는 카드 위에서 5.26이지만 페이지 배경 위에서는 4.68이다.
- **눈으로 판정하지 않는다.** 아래는 실측 사례(2026-07-27 재계산 확인) — 눈으로는 "읽히는 것 같은" 수준이었으나 전부 기준 미달이었다.

| 요소 | 색 변수 · 배경 | 최초(미달) | 조정 후 |
|---|---|---|---|
| 단계 설명 `.step-desc` | `--tx3` `#7c8ea4`→`#5b6e81` · 카드 `#ffffff` | 3.35 | **5.26** |
| 하단 고지문 `footer` | `--tx3` (같은 변수) · 페이지 `#eef2f7` | 2.98 | **4.68** |
| 대기 배지 `.state-wait .step-state` | `--wait` `#8496aa`→`#5c6f84` · `--waitbg` `#eef1f6` | 2.68 | **4.57** |

**대비비 계산** (배경·글자 색 두 개로 — 위 3행이 그대로 재현된다):

```bash
python3 -c "
def L(h):
    c=[int(h[i:i+2],16)/255 for i in (1,3,5)]
    c=[x/12.92 if x<=.03928 else ((x+.055)/1.055)**2.4 for x in c]
    return .2126*c[0]+.7152*c[1]+.0722*c[2]
def R(bg,fg):
    a,b=L(bg),L(fg); return round((max(a,b)+.05)/(min(a,b)+.05),2)
for bg,fg in [('#ffffff','#5b6e81'),('#eef2f7','#5b6e81'),('#eef1f6','#5c6f84')]:
    print(bg,fg,R(bg,fg))"
```

> 밝은 테마 고정(`color-scheme: light` + `meta name=color-scheme`)을 권장한다 — 브라우저 자동 어둠 반전이 대비 설계를 무너뜨린다.
