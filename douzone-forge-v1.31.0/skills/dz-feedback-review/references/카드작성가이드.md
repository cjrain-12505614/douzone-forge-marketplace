# 질문 카드 작성 가이드 (dz-feedback-review)

> 질문 페이지 카드의 글쓰기 규칙과 좋은 예·나쁜 예. 도구 사용법은 [`../SKILL.md`](../SKILL.md). §2·§4 의 실례는 2026-10-01 이 스킬을 다시 설계할 때 차민수 수석의 질문 페이지 1~3회차와 1단계 견본 검증에서 실제로 나온 것이다.

## 0. 원칙 한 줄

**사용자가 카드 하나만 읽고, 다시 묻지 않고 바로 고를 수 있게 쓴다.** 그러려면 선택지가 무엇인지 내용으로 적혀 있고, 고르면 무엇이 달라지는지 보이고, 자비스가 어느 쪽을 왜 권하는지와 그 대가가 함께 있어야 한다. 길이는 제한하지 않는다 — 대신 늘어나는 문장은 모두 판단 재료여야 한다.

## 1. 칸마다 쓰는 법

| 칸 | 쓰는 법 | 나쁜 예 → 좋은 예 |
|---|---|---|
| 리드(`lead`) | 이번 회차에 정할 것부터. 2회차부터는 직전 회차에서 무엇을 반영했는지 한 문장 | 「검토 부탁드립니다」 → 「1회차에서 한 줄 목록으로 정했고 시안 확인은 반나절로 줄였습니다. 이번에는 남은 두 가지를 정합니다」 |
| 카드 제목(`title`) | 고를 대상을 명사로 | 「질문 2」 → 「검색 결과를 고칠 때의 순서」 |
| 한 줄 요약(`summary`) | 무엇과 무엇 중에 고르는지 한 문장 | 「방식 검토」 → 「결과를 <b>한 줄 목록</b>으로 보여 줄지 <b>카드 묶음</b>으로 보여 줄지 고릅니다」 |
| 왜 묻는가(`why`) | 무엇이 걸려 있는지(나중에 바꾸면 무엇을 다시 해야 하는지), 지금 정해야 하는 이유 | 「중요한 결정입니다」 → 「한 번 정하면 필터·정렬·엑셀 내려받기가 그 모양에 맞춰 만들어져, 나중에 바꾸면 그 기능들을 다시 손봐야 합니다」 |
| 선택지 이름(`name`) | 무엇인지 내용으로(§2) | 「B안」 → 「카드 묶음 — 결과 한 건을 상자 하나로」 |
| 설명(`desc`) | 이름만으로 모자란 구체적 모습 | (비움) → 「결과마다 상자를 만들고 요약 두 줄까지 처음부터 보여 줍니다」 |
| 고르면(`then`) | 고른 뒤 달라지는 것 — 화면·일정·비용·되돌릴 수 있는지(§3) | 「장점: 직관적」 → 「누르지 않아도 요약이 보입니다. 한 화면에 보이는 결과가 줄어 스크롤이 늘어납니다」 |
| 추천(`rec`·`rec_text`) | 하나만, 이유는 이 상황에 맞춘 근거로 | 「일반적으로 좋습니다」 → 「검색은 여러 결과를 빠르게 훑는 일이 먼저라 한 화면에 많이 보이는 쪽이 낫습니다」 |
| 대가(`cost`) | 추천을 따르면 잃는 것 | 「특별히 없음」 → 「요약을 보려면 한 번 더 눌러야 합니다」 |

처음 나오는 용어·약어는 그 자리에서 괄호로 푼다(예: 「PoC(개념 검증 시안)」). 수치·일정·사람·출처는 확인한 것만 쓰고, 모르면 「확인 필요」라고 적는다.

## 2. 선택지는 내용으로 — 1회차 Q3 실례

### 나쁜 예 (실제로 냈던 카드)

1회차 Q3 「질문 카드에 펼쳐 둘 양」의 선택지는 이랬다.

| 번호 | 선택지 이름 | 설명 · 고르면 |
|---|---|---|
| ① | 질문·선택지·추천만 펼치고 배경·원본·근거는 「자세히」로 접기 | 고르면 지금 이 페이지 모양입니다. 카드 하나가 한 화면 안에 들어갑니다 |
| ② | v7 반영안 수준 | 쟁점·선택지·추천을 모두 펼칩니다(원본 격자·근거 목록은 없음). 고르면 카드마다 쟁점 문단이 길게 보입니다 |
| ③ | 1단계 견본 수준 | 원본 격자·해석·근거까지 모두 펼칩니다. 고르면 지금 견본처럼 문서가 길어집니다 |

차민수 수석의 답(수정): 「2,3번의 선택지 설명이 애매하다. 나는 접는것 없이 모두 펼쳐서 길더라도 이해하고 넘어가길 원한다. 설명도 명확히 해주면 좋겠어.」

무엇이 문제였나.

1. **「v7 반영안 수준」「1단계 견본 수준」은 자비스가 작업하며 붙인 이름이다.** 사용자는 그 문서들을 봤지만 「수준」이 카드의 무엇을 가리키는지(길이? 펼친 칸? 그림?) 이름만으로는 알 수 없다. 이름이 선택지의 내용을 대신했다.
2. 설명에 「원본 격자」「쟁점 문단」 같은 작업 중 용어가 풀이 없이 나왔다.
3. 「고르면」이 결과 대신 「지금 견본처럼」으로 다른 문서를 다시 가리켰다 — 결국 그 문서를 떠올려야 고를 수 있다.
4. 카드 자체도 배경을 「자세히」로 접어 두었다. 사용자는 접지 않기를 원했다(이후 모든 카드는 모두 펼침).

### 좋은 예 (같은 질문을 다시 쓴다면)

| 번호 | 선택지 이름 | 설명 | 고르면 |
|---|---|---|---|
| ① | 질문·선택지·추천만 처음부터 보이고, 배경 설명은 「자세히」를 눌러야 보임 | 카드 머리·선택지·추천만 펼쳐 둡니다 | 카드 하나가 화면 한 개 안에 들어갑니다. 배경을 읽으려면 카드마다 한 번 더 눌러야 합니다 |
| ② | 배경 설명까지 모두 처음부터 보임 — 엑셀 원본 표와 근거 목록은 넣지 않음 | 왜 묻는가 문단을 줄이지 않고 펼쳐 둡니다 | 누르지 않고 위에서 아래로 읽으면 판단 재료가 다 보입니다. 카드가 화면 한 개보다 길어질 수 있습니다 |
| ③ | 배경 설명에 엑셀 원본 표·해석·근거 목록까지 모두 처음부터 보임 | 원본 표를 카드 안에 그대로 옮겨 둡니다 | 원본을 따로 열지 않고 페이지 안에서 확인합니다. 1단계 견본처럼 A4 35쪽 분량까지 길어질 수 있습니다 |

이름이 곧 내용이고, 「고르면」은 화면에서 실제로 달라지는 것(한 화면에 들어가는지, 몇 번 눌러야 하는지, 얼마나 길어지는지)을 말한다. 이런 질문은 세 안의 카드 모습을 `.v-cols` 로 나란히 그려 보여 주면 글보다 빠르다(§5).

점검 질문: **사용자가 이 선택지 이름을 지은 적이 있는가?** 없으면 이름 대신 무엇인지 쓴다. 꼭 이름을 써야 하면 내용을 앞에 두고 이름은 괄호로 붙인다 — 「배경 설명까지 모두 펼침(9월 28일 OGSM 반영안과 같은 방식)」.

## 3. 「고르면」 쓰는 법

「고르면」은 장단점 목록이 아니라 **고른 뒤 무엇이 달라지는지**다. 다음 넷 가운데 해당하는 것을 구체적으로 쓴다.

- 화면·동작: 「한 화면에 결과가 많이 보입니다」 · 「요약을 보려면 줄마다 한 번씩 눌러야 합니다」
- 일정: 「시작이 하루 늦어집니다」 · 「다음 주 화요일에 첫 화면을 보여 드립니다」
- 비용·품: 「뒤따르는 기능(필터·정렬)을 다시 손봐야 합니다」
- 되돌릴 수 있는지: 「나중에 바꾸면 만든 화면을 다시 고쳐야 합니다」

| 나쁜 예 | 왜 나쁜가 | 좋은 예 |
|---|---|---|
| 「장점: 빠름 / 단점: 불편함」 | 무엇이 빠르고 무엇이 불편한지 없음 | 「시작은 빠르지만, 모양이 바뀌면 만든 화면을 다시 고쳐야 합니다」 |
| 「지금 견본처럼 됩니다」 | 다른 문서를 떠올려야 함 | 「A4 35쪽 분량까지 길어질 수 있습니다」 |
| 「유연하게 대응할 수 있습니다」 | 무엇에 어떻게가 없음 | 「세 안을 한눈에 비교합니다. 시안 안 표는 좁아서 줄바꿈이 많아집니다」 |

## 4. 다듬기로 불리지 않는다 — 1단계 견본 3.2배 실례

1단계(문서형 템플릿) 견본은 검증을 돌 때마다 「더 자세히」·문장 다듬기 지적이 쌓여 커졌다.

| 잰 것 | 처음 | 검증 7회차 뒤 |
|---|---|---|
| 본문 글자 수 | 11,162자 | 35,503자(3.2배) |
| A4 쪽수 | 10쪽 | 35쪽 |
| 첫 카드 높이 | 1,103px | 2,804px |

검증 5·6·7회차의 지적은 16건·14건·14건으로, 심각도는 내려갔지만 0건으로 줄지 않았다. 직전 회차에 고친 문장에서 새 다듬기 지적이 매번 14건 안팎 나왔기 때문이다. 그렇게 커진 견본은 사용자가 원한 것(질문하고 답받는 대화 환경)과도 어긋나 있었다.

그래서 이렇게 쓴다.

- 길이 제한은 없다(1회차 Q3 답 「길더라도 이해하고 넘어가길」). 대신 **문장을 하나 더 넣을 때마다 「이 문장을 빼면 사용자가 고를 때 무엇을 모르게 되나?」를 묻는다.** 답이 없으면 넣지 않는다.
- 같은 뜻을 다르게 쓰자는 다듬기 지적은 반영하지 않는다. 고치는 것은 틀린 사실·동작하지 않는 것·명세와 다른 것·사용자가 실제로 이해하지 못할 문장뿐이다.
- 왜 묻는가가 세 문단을 넘어가면, 그 내용을 그림·표로 바꿀 수 있는지 먼저 본다(§5).

## 5. 보여 주기 예

설명 한 문단보다 그림 하나가 빠를 때 그림을 쓴다. 장식용 그림(제목 옆 아이콘, 내용과 관계없는 일러스트)은 넣지 않는다.

### 흐름도 — 순서·단계가 걸린 질문

「시안으로 먼저 확인받고 개발할지」처럼 순서가 쟁점이면 단계를 그린다. 강조할 단계에 `is-key`.

```json
"visual": "<ol class=\"v-flow\"><li><span class=\"v-k\">1단계</span><b>시안 두 개</b><span class=\"v-d\">동작하는 HTML 로</span></li><li><span class=\"v-k\">2단계</span><b>질문 페이지</b><span class=\"v-d\">나란히 써 보고 고름</span></li><li class=\"is-key\"><span class=\"v-k\">3단계</span><b>고른 안으로 개발</b><span class=\"v-d\">한 번에 만듦</span></li></ol>"
```

1280 폭에서는 가로 화살표, 375 폭에서는 세로로 바뀐다.

### 나란히 비교 — 선택지마다 모습이 다른 질문

선택지 `visual` 에 그 선택지를 고르면 생기는 모습을 넣는다. 위 §2 Q3 같은 질문이면 선택지마다 「처음부터 보이는 것」과 「눌러야 보이는 것」을 칸으로 나눠 그린다. 아래는 ① 선택지의 예.

```json
"visual": "<div class=\"v-cols\"><div class=\"v-col is-key\"><p class=\"v-cap\">처음부터 보임</p><p>제목 · 한 줄 요약 · 선택지 · 추천</p></div><div class=\"v-col\"><p class=\"v-cap\">「자세히」를 눌러야 보임</p><p>왜 묻는가 · 원본 표 · 근거</p></div></div>"
```

2~3열까지 쓰고, 375 폭에서는 위아래로 바뀐다.

### 표 — 항목별로 따져야 하는 질문

```json
"visual": "<div class=\"tbl-wrap\"><table class=\"v-table\"><thead><tr><th>비교할 점</th><th>한 줄 목록</th><th>카드 묶음</th></tr></thead><tbody><tr><td>한 화면에 보이는 결과</td><td>많음</td><td>적음</td></tr><tr><td>좁은 화면(휴대폰)</td><td>글자가 잘릴 수 있음</td><td>그대로 읽힘</td></tr></tbody></table></div>"
```

### 동작하는 시안 나란히 — 써 봐야 고를 수 있는 질문

화면안·PoC·동작 방식은 글로 설명하지 말고 **두 안을 실제로 만들어 나란히 띄운다.** 선택지마다 `demo` 를 주면 카드에 「직접 써 보기」 칸이 생겨 1280 폭에서 시안 2개면 2열, 3개 이상이면 3열, 375 폭에서 위아래로 놓인다(써 보기 좋은 것은 2개까지).

```json
"options": [
  {"name": "한 줄 목록 — 결과 한 건을 한 줄로", "desc": "제목·날짜·담당자를 한 줄에 놓고, 줄을 누르면 요약이 펼쳐집니다.",
   "then": "한 화면에 결과가 많이 보여 훑어보기 빠릅니다. 요약은 줄마다 한 번씩 눌러야 봅니다.",
   "demo": "demo/search-poc-a.html", "demo_height": 380},
  {"name": "카드 묶음 — 결과 한 건을 상자 하나로", "desc": "상자 안에 요약 두 줄까지 처음부터 보여 줍니다.",
   "then": "누르지 않아도 요약이 보입니다. 한 화면에 보이는 결과가 줄어 스크롤이 늘어납니다.",
   "demo": "demo/search-poc-b.html", "demo_height": 380}
]
```

시안을 만들 때:

- **두 시안은 같은 예시 자료로 만든다.** 비교하려는 것(화면 모양·동작)만 다르고 나머지는 같아야 무엇이 다른지 보인다. 자료는 `data.json`·`data.js` 같은 따로 파일로 빼지 말고, 같은 변수(`var DATA = […]`)를 두 시안의 스크립트 안에 각각 복사해 넣는다(아래 「한 파일」).
- **시안은 HTML 한 파일이다.** CSS·JS 는 파일 안에, 그림은 인라인 SVG 나 `data:` 주소, 예시 자료는 스크립트 안 변수로. 시안은 sandbox(출처 없음)라 파일로 열면 같은 폴더의 `<script src>`·`<link href>`·`<img src>` 까지 모두 막히고, 창구로 열어도 `fetch`·`XMLHttpRequest`·`<script type="module">` 은 막힌다. `check` 가 이것을 `[문제]` 로 잡는다.
- **`body` 에 고딕 글꼴 목록을 적는다** — 안 적으면 맥 크롬 기본인 명조·Times 로 그려진다. 뼈대는 SKILL §6 「시안 뼈대」를 쓴다: `font:15px/1.6 "Pretendard",-apple-system,BlinkMacSystemFont,"Apple SD Gothic Neo","Malgun Gothic","맑은 고딕","Noto Sans KR","Segoe UI",sans-serif`.
- 실제로 반응해야 한다 — 검색어를 넣으면 걸러지고, 항목을 누르면 펼쳐진다. 그림만 있는 시안이면 선택지 `visual` 로 충분하다.
- 시안 하나는 비교에 필요한 화면 하나만. 시안 안 상태는 변수로 들고 있는다 — `localStorage`·쿠키는 쓰지 않는다(카드 칸과 「새 창으로 크게 보기」 창에서는 sandbox 라 오류가 나고, 시안 파일을 직접 열면 sandbox 밖이라 질문 페이지 저장값에 닿을 수 있다).
- 외부 자원·세리프 글꼴·이모지 금지는 시안에도 똑같다 — `check` 가 시안 파일까지 본다.
- 시안을 나란히 두는 것은 두 개까지가 읽기 좋다. 세 개를 두면 1280 폭에서 한 칸이 좁아 시안 안 표·긴 글이 줄바꿈된다.

## 6. 내기 전에 점검

- [ ] 카드 안에 접는 요소(「자세히」·`<details>`)가 없다
- [ ] 선택지 이름이 내용이다 — 자비스가 붙인 이름·약칭·파일명으로 대신하지 않았다
- [ ] 선택지마다 설명과 「고르면」이 있고, 「고르면」은 달라지는 것(화면·일정·비용·되돌릴 수 있는지)이다
- [ ] 추천은 하나이고 이유와 대가가 있다(정말 판단 재료가 부족할 때만 추천 없음)
- [ ] 리드와 왜 묻는가가 결론부터 시작한다
- [ ] 처음 나오는 용어·약어를 그 자리에서 풀었다
- [ ] 수치·일정·사람·출처는 확인한 것만 썼다
- [ ] 긴 설명 가운데 그림·표로 바꿀 수 있는 것은 바꿨고, 써 봐야 고를 수 있는 선택지는 시안을 만들었다
- [ ] 장식용 그림이 없다
- [ ] 시안은 HTML 한 파일이고(다른 파일·fetch 없음) `body` 에 고딕 글꼴을 적었다
- [ ] `fbq.py check --render` 가 통과했다
